### ディレクトリを近くに

```bash
src/app 
├── orgs 
│   ├── org-list.tsx 
│   ├── use-orgs.ts 
│   ├── org.ts 
│   └── page.tsx 
└── pull-requests
    ├── pull-request-list.tsx 
    ├── use-pull-requests.ts 
    ├── pull-request.ts 
    └── page.tsx 
```

<!-- 
これがCo-locationです。( Package by Featureとも呼ばれます )
components, hooks, utilsなどの役割ごとにディレクトリを分けるのではなく、機能ごとにディレクトリを分けることで、関連するコードを近くに配置します。
usersというディレクトリはもともとusersに関連するコードを集める目的の命名がされているので、そこに集めることが自然です。
カテゴリごとにコードを分けなくても、ファイル名を見ればそれがどのカテゴリのコードなのかわかりますよね。
なので、近くに置けばディレクトリを作らなくても良くなり、ネストも浅くなります。
結果的に、ファイルの数自体は変わっていないのに、把握すべきフォルダが減りました。

こうならないために意識すべきことは、hooks, components, typesという名前のディレクトリ、ファイルを作らないことです。

ここまでは、もしかしたら皆さんよく知っている話かもしれません。
1ファイル1コンポーネント・1ファイル1フックという“形式的なルール”が、かえってコードを分断することもあります。 
そこで次は、「ファイルの中のまとめ方」を見ていきましょう。
 -->

### 関連するコードは近くに

```tsx: user-list.tsx
const usePullRequests = () => {
  // プルリクエスト一覧を取得するロジック
  return [
    { id: 101, title: "Fix validation for full-width/half-width" },
    { id: 102, title: "Add organization filter API" },
  ];
};

export function PullRequestList() {
  const pullRequests = usePullRequests();

  return (
    <ul>
      {pullRequests.map((pr) => (
        <li key={pr.id}>{pr.title}</li>
      ))}
    </ul>
  );
}
```

<!-- 
そのコンポーネント専用のロジックなのであれば、同じファイルにまとめてしまいましょう。
「ここで、よくある疑問にお答えします。 『全部1つのファイルに書いたら、ファイルが長くなりすぎて読みにくくなりませんか？』

私の答えはこうです。 『文脈が分断された短いファイル10個よりも、文脈が繋がった長いファイル1個の方が、読みやすい場合が多い』

もちろん、千行単位になってしまうのであれば、分割を検討すべきです。しかし、あくまで基準は『行数』ではなく『意味のまとまり』です。 スクロールするだけで読めるのか、ファイルジャンプが必要なのか。認知負荷が低いのは、実は前者であることが多いのです。」

特に、最近では1ファイルに全てがまとまっているメリットが増してきましたよね。
そう、コーディングエージェントです。
私の基準は、コンポーネントが3層以上ネストする場合には分割を検討します。
 -->

### なぜコードを遠ざけてしまうのか

- 見かけ上のわかりやすさ
  - ファイルが短いと見やすい
  - ルールで決めやすい
- 昔のフレームワークの制約の名残

<!--
なぜコードを遠ざけてしまうのでしょうか。
この設計の変更は、新機能の追加や、一部のモジュールだけのリファクタリングからすぐに始められます。
AIが出力する際になにも参考にするものがないと、分散したコードが出力されてしまう事が多いです。

## 脳内のリソースを意識しよう

<!-- 
開発者がコードを読むとき、その処理内容だけでなく「その処理がどの条件分岐の中にいるか」も同時に記憶しようとします。
これは脳の認知リソース（ワーキングメモリ）を消費します。
if文を書くときに、主要な処理（正常系）を深いネスト（入れ子）の中に置いていませんか？
 -->

---

```tsx: order-status.tsx
function OrderStatus({ user, order }: { user: User | null; order: Order }) {
  // 1. ログインしているか？
  if (user) {
    // 2. 注文項目があるか？
    if (order.items.length > 0) {
      // 3. 残高が足りるか？
      if (user.balance >= order.total) {
        
        // 🟥 正常系が一番深い階層に入り込んでいる
        return <p>注文ID {order.id} の処理が完了しました。</p>;

      } else {
        return <p>残高が不足しています。</p>; // 異常系3
      }
    } else {
      return <p>注文品目がありません。</p>; // 異常系2
    }
  } else {
    return <p>ログインしていません。</p>; // 異常系1
  }
}
```

<!-- 
このようなコードは、コードを読み進めていく中で「ユーザーがいて、品目があって、残高がある...」という複数の前提条件を同時に頭の中に認識として残して先に進むことになるため、非常に読みにくいです。
 -->

---

```tsx: order-status.tsx
function OrderStatus({ user, order }: { user: User | null; order: Order }) {
  if (!user) {
    return <p>ログインしていません。</p>;
  }

  if (order.items.length === 0) {
    return <p>注文品目がありません。</p>;
  }

  if (user.balance < order.total) {
    return <p>残高が不足しています。</p>;
  }

  // ---- ここから正常系 ----
  return <p>注文ID {order.id} の処理が完了しました。</p>;
}
```

<!-- 
先に不要な処理（異常系）を一括で終わらせておき、最後に正常系を書きます。
このようにすることで、読み手が「この時点ではすべての前提条件がクリアされている」と認識を更新でき、考慮すべきことを後に残さずに読み進めることができます。
加えて、異常系が複数で、正常系は1つであることがほとんどです。 
このような書き方に統一することで、**関数の最後を見れば必ず正常系** という共通の構造に統一することができます。
 -->

## まとめ

1. Co-location: 関連するコードは近くに配置する
2. Top-down: 重要な（公開する）処理を先頭に書く。
